# Start here: task first, stack second

Create and install a skill named `code-index` (Start here: pick skills by task). It instructs the agent as follows: Your installed skills each do one job — never read them all. Step zero: detect the codebase's language, framework, and tokens before matching anything. Bound to a stack? The house defaults never apply — follow the codebase and skip or overwrite every conflicting house skill. We default to Python plus FastAPI plus Pydantic and Lit only for new, unbound work because agents generate it fastest with the fewest mistakes — never force it on an existing codebase. Work in two passes. Pass 1 — task first. Three skills apply to almost every task, so always read these: code-secure, code-reuse, code-token. Then match the task and read only the matched skills — mixed tasks match more than one line, so a UI-plus-API job reads ui-index and the service skills: Interface, screen, or component work → ui-index. New service or script → code-language, code-shape. Organizing a new codebase → code-group. Services in other languages → code-boundaries, then code-polyglot for the guest side. Public API, forms, beacons → code-ratelimit. Repeat traffic → code-cache. Usage counts → code-track. Slow endpoint or heavy page → code-perf. Traffic spikes, shedding features → code-fallback. Login, accounts, permissions → code-auth. Product features (billing, roles, admin — any SaaS, SIS, billing system) → app-index. Landing data and scheduling pipelines → data-index. Build-test-deploy gates and paging → ops-index. Vuln deadlines, enterprise login, regulated data → sec-index. Security deep-dives — the OWASP Top 10 set, read on match: code-crypto, code-injection, code-design, code-misconfig, code-deps, code-integrity, code-logging, code-ssrf. Pass 2 — stack specifics. After the task match, apply the stack the codebase already uses: language → code-language (Python first on new code; if the project already uses another language, skip this skill or overwrite it with that stack). Interface framework → ui-index (house default Lit via ui-framework; widget libraries per framework live in ui-platform-picks). Styling → ui-tokens (unless the project already has a design system — then skip it). Mobile platform → ui-mobile (Capacitor shell unless native is technically required). Service-to-service → code-boundaries (same-language HTTP, other languages gRPC, events validated). These stack picks assume a new codebase: if the project already uses something else — another language, framework, tokens, or platform — follow that instead. The house rule beats the skill. Skip everything else. Fetch all matched skills in one batched request; never fetch the same skill twice in one session — installed skills live locally. When building is done → verify-tests, plus verify-visual for screens and verify-layout for layout. Three or more matched skills → code-plan first. Missing a skill? Copy its prompt from the skills page once, install it, then use it locally. This follows progressive disclosure — map first, details on demand.

## Checks

- only matched skills are read
- always-on skills never skipped
- whole bank never copied at once
